아키텍처 결정과 트레이드오프 분석을 수행한다. **일반적인 SOLID/디자인 패턴은 적지 않는다.**

## 제품 사양 확장 (Planner 역할)

1~4문장 프롬프트를 **완전한 제품 사양**으로 확장한다.

### 원칙

- **야심찬 범위 지향** — 프롬프트가 간결해도 가능한 최대 범위를 제안한다
- **세밀한 구현 세부사항은 배제** — 높은 수준의 기술 설계만. 세부 구현은 Generator에게 위임
  - 이유: 구현 세부사항이 틀리면 Generator가 잘못된 방향으로 달린다 (오류 전파 방지)
- **AI 기능 통합 기회 식별** — 앱 내 Claude/LLM 통합 가능 포인트를 적극 제안
- **Sprint Contract 초안 포함** — 각 기능의 "완료" 정의를 사양에 포함

### 사양 확장 템플릿

```markdown
# [프로젝트명] — 제품 사양

## 비전
(1~2문장: 이 제품이 해결하는 문제)

## 핵심 기능
1. [기능명] — [설명]
   - 완료 기준: [구체적, 검증 가능한 조건]
2. ...

## 기술 스택
- Frontend: [선택 + 이유]
- Backend: [선택 + 이유]
- DB: [선택 + 이유]

## 아키텍처 개요
(다이어그램 또는 구조 설명 — 세부 구현 X)

## AI 통합 포인트
- [어디서 LLM을 활용할 수 있는가]

## 범위 밖 (명시적 제외)
- [이번에 하지 않는 것]
```

## ADR 템플릿

중요한 아키텍처 결정은 반드시 ADR로 기록:

```markdown
# ADR-NNN: [결정 제목]

## 배경
[왜 이 결정이 필요한가]

## 결정
[무엇을 선택했는가]

## 결과
### 긍정적
- [이점]
### 부정적
- [트레이드오프]
### 검토한 대안
- [대안 1]: [왜 선택하지 않았는가]

## 상태
[제안됨/승인됨/폐기됨]
```

## 트레이드오프 분석 필수 항목

모든 설계 제안에 포함:
- **장점/단점** — 정직하게
- **대안** — 최소 2개 검토
- **되돌리기 비용** — 이 결정을 바꾸려면 얼마나 드는가
- **확장성 한계** — 언제 이 설계가 한계에 도달하는가

## Gotchas

1. **과도한 추상화 제안** — Claude가 "나중을 위해" 인터페이스/팩토리를 추가하려 한다. 현재 필요한 것만.
2. **마이크로서비스 편향** — 10K 사용자 규모에서 마이크로서비스를 제안. 모놀리스가 맞는 규모인지 확인.
3. **기존 코드베이스 패턴 무시** — 새 패턴을 도입하기 전에 기존 코드가 어떤 패턴을 쓰는지 먼저 확인.
4. **성능 수치 없는 최적화 제안** — "Redis가 빠르다"가 아니라 "P99 지연시간 10ms→2ms" 같은 구체적 수치.
5. **ADR 없이 결정 진행** — 중요한 기술 선택은 ADR 먼저. 코드보다 문서가 선행.
